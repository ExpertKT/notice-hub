# 架构

维护者看的一页。只写事实：东西在哪、怎么连起来、数据放在哪。

## 目录分层

| 位置 | 里面是什么 |
| --- | --- |
| `main.py` | CLI 入口：`run`、`tick`、`preview`、`stats`、`show`、`tasks`、`catchup`、`doctor`、`send-test`、`attach-test` |
| `noticehub/` | 全部业务代码 |
| `noticehub/web_static/` | 网页前端：`page.html`、`js/*.js`，没有构建步骤，改完刷新就是新的 |
| `packaging/` | 出货包：启动器、托盘、安装脚本、各平台打包 |
| `tests/` | 单测与浏览器级用例 |
| `docs/wiki/` | 这一套文档 |

## `noticehub/` 里的分层

| 模块 | 职责 |
| --- | --- |
| `receiver.py` | 接收 NapCat 的 OneBot v11 HTTP 上报，落库 |
| `store.py` | SQLite：消息、待办、去重、完整性检查与恢复 |
| `summarizer.py` | 把一批消息归纳成待办、截止时间、推送文本；模型失败回退本地规则 |
| `service.py` | 调度、合并窗口、补采、重试、生命周期 |
| `push.py` | 推送通道与失败回退 |
| `webapp.py` | 网页与 HTTP 接口：待办台、月历、收件箱、设置、更新 |
| `napcat_admin.py` | NapCat 探测、安装、启停、写配置、登录二维码 |
| `hosting.py` | 托管切换（关 QQ / 起 NapCat / 还原）与状态持久化 |
| `config.py` / `bootstrap/settings.py` | 读 `.env` 与环境变量，新旧前缀兼容 |
| `config_audit.py` | 把「实际生效的值 + 它从哪来」汇成表，设置页的「配置体检」用它 |

网页相关的接口按功能拆过一轮：路由表、设置接口、更新接口各自独立，`webapp.py` 从 4403 行降到 3697 行，行为不变。

## 进程与端口

| 进程 | 作用 |
| --- | --- |
| `QQ-Notice-Hub.exe` | 启动器：单实例互斥、托盘、看门狗（每 2 秒查一次服务，按 5/15/45 秒退避重启） |
| `qq-live-digest.exe` | 真正的服务进程 |
| NapCat | 独立的 QQ 协议客户端，由群务台启动时用**独立资料目录** |

| 端口 | 用途 |
| --- | --- |
| `8766` | 网页、手机端、日历订阅 |
| `8765` | NapCat 往群务台推 OneBot 上报 |
| `3001` | 群务台反查 NapCat 的 HTTP API（补采、状态、二维码） |

防火墙规则只对「专用 / 域网络」和本机网段放行。公用网络下手机连不上是刻意的。

## 数据落在哪

| 路径 | 内容 |
| --- | --- |
| `安装目录\.env` | 配置 |
| `安装目录\data\` | SQLite 数据库、附件缓存、学习通 Cookie、日历链接 |
| `安装目录\logs\` | 运行日志、启动器日志 |
| `data\*.corrupt-<时间戳>` | 启动时完整性检查不通过而被隔离的旧库 |

- 备份就备份 `data\`。
- 数据库每天自动快照，保留 7 份。
- 设置页的「一键备份」导出的 ZIP 里只有 SQLite，不含配置、令牌、日志。

## 一次消息怎么变成待办

1. NapCat 把群消息 POST 到 `8765`。
2. `receiver` 落库；不在 `NOTICEHUB_GROUPS` 白名单的群直接丢。
3. `service` 按合并窗口把消息攒批，交给 `summarizer`。
4. `summarizer` 产出待办（标题、截止时间、置信度），拿不准的先进「候选」。
5. `push` 按通道发出去，失败走回退。
6. `webapp` 的 `/api/tasks` 和 `/calendar.ics` 把结果给网页和手机。

## 对话里的校园规划工具

`application/agent_chat.py` 把待办和可用地点表交给模型。模型返回 `{"say":"…","calls":[…]}`，服务端执行工具，把结果追加为下一跳的「工具结果」，同时返回到 `/api/agent/chat` 的 `trace`。每轮最多两跳、每跳最多三个调用；收尾保留模型读过工具结果后的最后一句非空回复，没有这类回复才使用工具摘要。首跳执行前的计划句不算执行结果。

`{"name":"day_plan"}` 无必填参数，直接复用 `application/agent_plan.today_plan(store, settings)`，与页面今日行程使用同一份课表、待办、常做事项和地点校准。完整结果回传模型及 `trace.result`，包括每趟区域、起止时间、站点顺序与到离时刻、办理分钟和原因、距离和步行分钟，以及 `counts`、`unscheduled`、`overflow`、`warnings`、`checks`。它不写待办；空行程也给出说明。模型回答今日安排时先调用它，只引用返回的时刻和数字，不能因此新建待办。该工具沿用今日排程的 70 米/分钟口径和办理时间。今日候选只保留无截止日期或截止日期不晚于规划日的待办；未来日期的待办放进 `unscheduled`，标明日期与未排原因。

`application/route_tools.py` 复用 `campus.load_pois` 的地点数据和 `trips` 的距离、最近邻计算。工具只读数据，`changed` 为 false：

- `{"name":"plan_route","points":["立行楼","图书馆","立德楼"],"start":"学生公寓A"}`：`points` 为 1–64 个楼名、别名或 POI 编号；`start` 可省略，省略时固定首点起步。同一 POI 只访问一次，不要求回到起点。输入最多 8 点时枚举全部顺序求精确解，超过 8 点用最近邻加 2-opt，并保证不比输入顺序长。返回 `order`、`poi_ids`、各段 `legs`、`distance_m`、`walk_minutes`、`input_distance_m`、`saved_m`、`algorithm` 和距离口径 `basis`。
- `{"name":"poi_near","place":"图书馆","radius_m":300}`：半径包含边界与所在楼；返回 `places` 的地点与距离，以及 `tasks` 中已有的未完待办。只有待办标题能匹配地点时才入选，不会虚构办事项目。附近不等于沿途，不保证营业、截止时间或可办理；需要合并路线时继续调用 `plan_route`。

工具结果在 `trace` 保留原参数 `args`、成功标志 `ok`、可读结论 `detail` 和结构化 `result`；无地点、空输入、非法半径或坐标返回可读错误。模型没写总结时仍返回工具结论。

距离按米制平面欧氏距离计算，步速固定为 **70 米/分钟**（与行程面板同一个常量 `trips.WALK_M_PER_MIN`；以前这里写死 75，同一段路两个面板报两个时间）；米数保留一位、分钟两位，比较和优化都用未舍入值。它没有道路、进楼和办理时间，不能当实地步行导航。`campus.py` 内置常州大学西太湖校区 27 处地点：11 栋宿舍、2 个餐厅、图书馆、图文信息中心楼、8 栋教学（马士、白云、武进、汤湖、立德、立功、立言、立行）、立艺楼、汤湖体育馆、运动场，外加博雅居片区点。代码里只留名字、别名、分区、层数与开放时间，坐标全在 `js/campus-geo.json`（快照像素平面，原点取校区西北角、x 向东、y 向南）；每处地点带一个 `src` 说明坐标怎么来的——`osm`（OSM 上有名字的楼面质心）、`osm-footprint`（有面没名字，按平面图换算配号）、`estimated`（OSM 没面，经同名楼拟合的相似变换换算，约 ±20 米），选底色时估算点画虚线。这仍是示意图上的估算，未核实实地入口、层数和营业时间；营业时间留空。部署时通过数据目录的 `campus_poi.json` 按相同 id 覆盖，所有点须处于同一坐标系；坐标需有限且绝对值不超过 10,000,000 米。旧覆盖文件和已保存待办不会自动迁移，旧楼名不再由默认表猜测匹配。图书馆与图文信息中心楼是两处，相距约 100 米，各占一条；博雅居是一片宿舍区，单独登记，不挂到某一栋。

地点坐标来源：楼块位置来自 `js/campus-geo.json` 的经纬度，按 `js/campus-osm.js` 那份校园快照的同一条投影换算到米制平面（0.9 米/像素，x 向东、y 向南）；底图里的校区边界、环路与主路、绿地、水面、跑道取自同一份快照。这份快照是从 OpenStreetMap 抓的校园周边几何，**属于 OSM 的派生数据，按 ODbL 1.0 使用**：底图角落常驻「© OpenStreetMap contributors, ODbL 1.0」那一行（`trip.js` 里按底图档切换 `MODES[].credit`，由 `.map-credit` 显示，手机上抬到说明条上方），来源与许可也写在 `campus-osm.js` 的文件头。再分发本项目时，这份几何数据（及其派生的 `campus-geo.json`）要一并保留署名、同样以 ODbL 提供。楼名、别名、楼层、开放时间这些文字是自己填的。演示种子房号与办事项目是样本，不代表真实楼内窗口。

演示种子（`demo/seed.py`）今天是 5 站、2 趟、合计 **991 米**，按 70 米/分钟折 **14 分钟**：第 1 趟 565 米（立德楼 → 立行楼 → 图书馆），第 2 趟 426 米（第一餐厅 → 1 号楼）。「交大学物理实验报告 武进楼B203」截止明天 18:00，不进今天的行程，单列进「排不进去」并写明理由。这些都是种子数据的直线距离，未验证实测坐标或实际步行距离；旧演示文案里的 6 件 / 997 米 / 1166 米 / 走路 16–18 分钟都已作废，别再引用。

## 更新链路

1. 检查更新：按通道（stable / beta）查 GitHub Releases。
2. 清单里每个包的 `sha256` 必须存在；下载域名只认 GitHub 和 Gitee。
3. 下载：两个源版本与 SHA-256 一致时优先走 Gitee，否则保持 GitHub；有超时和「放弃下载」。
4. 覆装前先看目标文件有没有被占用，被占就整包放弃，不留半装状态。
5. 装完由托盘「重启并更新」触发重启；服务没起来会重试 3 次，仍失败会提示手动启动。

Linux 只能检查和下载，安装要手动。macOS 暂未适配（安装脚本 `packaging/macos/` 保留但未验证）。

## 安全边界

- 访问令牌换 HttpOnly 会话 Cookie，地址栏不留明文 token，也不写 localStorage。
- 连续的失败鉴权会被限速；HTTP 请求 30 秒超时、并发连接上限 64。
- NapCat 安装包解压前校验指纹，首次要人工确认一次实算值。
- 日志与「配置体检」都不回显 token、key、Cookie 原文。

改代码的规矩见仓库根的 `AGENTS.md`；改动要落进 [更新日志](changelog.md)。
