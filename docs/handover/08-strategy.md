# 08-strategy.md — 重写期间发布策略：选 A 还是 B

**结论：选 B（继续发版），但加三条限制。**

---

## 1. 两个选项的真实成本

| | A. 暂停发版 | B. 继续发版 |
|---|---|---|
| 用户拿到 bug 修复 | 要等重写完（未知周期） | 照常 |
| 重写分支的工作量 | 少一件：不用管合并 | 多一件：每个发版都要评估是否并入 |
| 回退能力 | 无（重写完才能发） | 有（老版本仍是发布态） |
| 用户感知 | 「项目停了」 | 正常 |
| CI | 5 个 job 照跑 | 同左，外加 clean-room 分支自动触发 |

## 2. 选 B 的理由

**最主要的一条：暂停发版会让已知的 bug 无限期留在用户手上。**

当前工作区就压着两族**已修好、已验证、还没发**的修复：

- 社区在线数永远显示「暂不可用」（三层根因叠加，见 history.md 第 20 条）
- 服务自检 32.7 秒 → 10.2 秒（同一请求里状态算两遍 + tailscale 子进程跑两次）

这两族都是用户当场看到并报回来的。暂停发版 = 用户继续用着坏的界面等重写。
而重写周期以「周」计，不是以「天」计。

**次一级的三条：**

1. **重写不覆盖全部功能。** clean-room 的范围是 `domain` / `ports` / `application` /
   QQ 适配 / 存储 / 配置 + 11 个上游测试。**微信、钉钉、学习通接入、NapCat 托管、
   打包、自动更新、安卓端、托盘都不在重写范围内。** 暂停发版等于把这些也一起冻结。
2. **暂停期间攒的改动更难合。** 重写分支拉出去越久，`main` 上的偏差越大。
   与其攒一大堆一次合，不如每个发版都评估一次。
3. **CI 已经能兜住。** `.github/workflows/tests.yml` 是 `on: push / pull_request`，
   **推 `rewrite/clean-room` 会自动跑全量测试**（见 tests.md）。
   发版不会因为重写分支存在而被拖坏——两边各有各的 CI。

## 3. B 的三条限制（不加这三条，B 会变成灾难）

**限制 1：clean-room 分支不许反向合并进 `main`，直到 G4 验收通过。**

`main` 继续收 bug 修复和小功能；重写成果只在 clean-room 分支上累积。
G4 验收通过后才按两阶段策略合并（见 risks.md 第 4 节）。
理由：`webapp.py` 的 255 条 `PAGE_SOURCE` 断言和 `service.py` 的双向依赖意味着
半成品合进来会让 `main` 的测试全红，而 `ci-green` 是推 `main` 的硬标准。

**限制 2：每个发版前必须核对一次「是否已被重写覆盖」。**

具体动作：发版前跑一次 `git log --oneline main ^rewrite/clean-room`（或反向），
看有没有两边都改过的文件。有就记录下来，供合并时逐个处理。
成本：一条命令，几分钟。
不做这条的后果：合并时靠记忆，必漏。

**限制 3：`main` 上的改动必须保持「可被 clean-room 吸收」的形状。**

也就是继续遵守并行期间的边界（`dsh-handoff.md` 第 3 节）：
清单内文件不重构、最小提交、不改公开函数签名、新功能优先落在 `webapp.py`/前端/打包侧。
这条**主要约束的是 `main` 这边的开发纪律**，不是重写方。

## 4. 合并成本估算

按当前结构算，不是乐观值：

| 阶段 | 工作量 | 说明 |
|---|---|---|
| 新模块与旧模块并存 | 3–5 人日 | 写适配层，让两套能同时被 import；跑通全量测试 |
| 切换调用点 | 5–8 人日 | 主要是 `service.py` 的依赖反转 + `webapp.py` 的 `self.server.*` 反向取用 |
| 删旧实现 | 1–2 人日 | 删完必须全量测试 + 冷装 + 更新演练重跑 |
| 包名/模块重命名（最后一个提交） | 0.5–1 人日 | 一次性完成，含 `spec`、`launcher.py`、CI、文档 |
| **合计** | **约 10–16 人日** | 前提：G1 契约一次定死；若契约返工，乘 1.5 |

`dsh-handoff.md` 第 5 节「G1 契约出来之前不要把 webapp 逻辑往新分层迁移」这条
**必须遵守**——契约返工一次的代价比上面整张表还大。

## 5. 什么情况下改选 A

只有一种情况值得暂停发版：**clean-room 已经能独立跑通核心链路，且 `main` 上连续两个
版本都是纯 UI/文案改动**（即没有值得发的修复）。此时暂停省下的合并评估成本 > 用户损失。
当前不符合：工作区还压着两族已验证的功能修复。

---

## 必须由人补的项

1. **重写的实际周期**（决定 B 的限制 2 要执行多少次）。外派方排期未知。
2. **`main` 上还会不会有「清单内文件」的改动需求**——如果用户在重写期间要求改
   `store.py`/`service.py` 核心逻辑，限制 3 会被打破，需要重新决策。
3. **G4 验收由谁签**（原流程是项目 Lead B；当前 B 已退出，需明确接手人）。
